# Базовые ограничения безопасности

**Когда брать:** сразу после `02-hooks.md`, до работы с приватными данными.
**Результат:** проверенная конфигурация разрешений и локальная проверка индекса Git.

`permissions.deny` запрещает совпавший вызов; `permissions.ask` требует подтверждения.
Это разные механизмы. Bash-правила используют wildcard, не regex, и не являются
границей безопасности: другие формы команд, Python/Node и дочерние процессы могут
читать файлы и отправлять данные. Read-правила не блокируют косвенное чтение через Bash.
Образец settings — отправная точка, не гарантия защиты от удаления или утечки.

## Промпт

```prompt
Настрой базовые правила в .claude/settings.json на основе
templates/claude-settings.json.example. Не заменяй файл целиком: сохрани существующие
hooks/permissions, покажи только план и очищенный от секретов diff.

1. Сверь синтаксис с документацией установленной версии Claude Code.
2. Добавь deny для указанных опасных форм rm/curl/wget и прямого чтения .env,
   .env.*, вложенных env и файлов ключей. Объясни ограничения каждого правила.
3. Не читай реальные секреты ни целиком, ни выборочно. Значения не должны попадать
   в чат, логи или команды. Пользователь вводит их в secret manager самостоятельно;
   агент проверяет только имена обязательных переменных и факт настройки.
4. Не включай Bypass Permissions. Он допустим только по отдельному решению владельца
   в изолированной VM/контейнере без production-секретов, с ограниченной сетью.
   Git-коммит не заменяет резервную копию: он не восстанавливает ignored-файлы,
   внешнюю БД/облако и уже отправленные данные. Нужны отдельные backup/restore-тесты.
5. До ввода бизнес-данных исключи .business/ из индекса и будущих коммитов.
   Не скрывай ошибки Git. Untrack/ignore не удаляют данные из истории.
```

## Проверка без риска

Используй одноразовую тестовую папку и фиктивный `.env` без секретов. Проверь разбор
settings и отказ для deny-совпадений, не выполняя разрушительные команды на проекте.
Для ask ожидается запрос, для deny — отказ. Не тестируй отправку настоящих данных.

## Проверка коммитов

- `python3 scripts/check_secrets.py --staged` проверяет добавленные/изменённые blobs
  индекса, а не рабочие файлы. Удаления разрешены. Пробелы и переводы строк в именах
  обрабатываются через NUL-разделители Git; содержимое находок не печатается.
- `bash scripts/security-audit.sh` проверяет **весь индекс**, включая scripts/hooks/tests.
  Локально сначала добавь в индекс только намеченные файлы поимённо. CI проверяет checkout.
- `.env` и `.env.*` запрещены; только `.env.example` и `.env.sample` допускаются по имени,
  но их содержимое тоже сканируется. Используй пустые значения, `<YOUR_API_KEY>` или
  `${YOUR_TOKEN}`, а не реальные/похожие на реальные ключи. Локальные MCP/settings,
  credentials.json и файлы `.pem`/`.key` также не предназначены для публикации.
- Для hook сначала проверь `git config --get core.hooksPath` (код 1 означает, что
  настройка не задана) и `git rev-parse --git-path hooks`. Просмотри существующий
  pre-commit. Только если его нет, вручную установи sample в выбранный каталог и
  выдай право исполнения. Если есть — согласуй интеграцию, не перезаписывай его.
- Запусти `python3 -m unittest discover -s tests -p 'test_*.py' -v`.

Код 0 означает только отсутствие совпадений известных эвристик. Это не полный аудит
секретов, персональных данных, зависимостей или истории. Находки выводятся по номеру
проверяемого blob без строки/значения/имени файла; разбирай их локально, не публикуй
сырой вывод Git. При ошибке сканирование завершается ненулевым кодом.
Для публикации нужен отдельный аудит истории и ручная проверка; для реальной утечки —
сначала отзыв/ротация ключа, затем согласованная очистка. Hook можно обойти, а CI сам
не настраивает branch protection или запрет деплоя: required checks включаются отдельно.
