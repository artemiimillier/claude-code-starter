# Деплой с проверкой готовности

**Когда брать:** код подготовлен к публикации, есть владелец релиза и тестовое окружение.
**Результат:** проверенный релиз либо честный список блокеров. Доступный URL — только
smoke-test, не доказательство безопасности или готовности production.

## Выбор платформы

| Платформа | Типичный сценарий | Что проверить до решения |
|---|---|---|
| Vercel | Frontend, Next.js, статика | Ограничения runtime, тариф и условия коммерческого использования |
| Railway | Приложение с сервером/БД | Стоимость ресурсов, регион, backup и восстановление |
| Amvera | Размещение в РФ | Договор, фактические регионы хранения и обработки, внешние интеграции |
| Свой сервер | Контроль инфраструктуры | Обновления, TLS, firewall, мониторинг и ответственный администратор |

Тарифы, пробные кредиты и возможности меняются: сверь официальные условия перед
платным действием. Размещение в РФ само по себе **не гарантирует соответствие 152-ФЗ**.
Нужны анализ потоков ПДн, оснований обработки, договоров, локализации и трансграничных
передач (включая аналитические/AI API), при необходимости — профильный юрист.

## Промпт для выбранной платформы

```prompt
Подготовь деплой на [Vercel / Railway / Amvera / свой сервер].
Не покупай ресурсы и не публикуй production без моего подтверждения.

1. Проверь стек и актуальную официальную документацию платформы. Покажи план,
   оценку расходов, регион, выбранный репозиторий/ветку и изменения конфигурации.
2. Сначала используй preview/staging. Дай инструкции для входа и подключения репо;
   авторизацию и секреты я ввожу самостоятельно в панели/secret manager.
3. Перечисли только ИМЕНА обязательных env и их назначение. Не проси значения в чате,
   не читай/печатай их и не сохраняй в git, build-логах или клиентском bundle.
   Раздели preview/production credentials, примени минимальные права.
4. Создай нужные build/start-конфиги. Выполни тесты, lint/build и проверку индекса
   bash scripts/security-audit.sh. Нулевой код сканера не заменяет аудит истории.
5. Проверь в staging TLS, health endpoint, auth и авторизацию: анонимный пользователь
   не видит приватные данные, пользователь A не получает данные B, admin API закрыт.
   Проверь миграции и обработку ошибок. Формы/платежи/письма — только в sandbox
   с тестовыми данными и заглушками внешних отправок.
6. Если есть БД или хранилище — сделай отдельный backup, проверь восстановление в
   изоляции. Согласуй миграции, совместимость отката, предыдущий артефакт и план rollback.
7. Настрой health monitoring и оповещения, согласуй ответственного за сбой.
   Автодеплой production включай только после настройки required CI checks и правил
   ветки/окружения с одобрением релиза, а не просто на каждый push.
8. Покажи отчёт с фактическими результатами и блокерами; запроси разрешение на релиз.
   После разрешения выполни деплой, проверь health/TLS и безопасный smoke-test.
   При провале используй согласованный rollback и проверь восстановление сервиса.
```

## Приёмка

- [ ] Ссылка доступна с телефона и с внешней сети; TLS корректен.
- [ ] CI, build и согласованные auth/access-тесты прошли; skipped не выданы за passed.
- [ ] Секреты не в клиентском коде; prod и sandbox разделены.
- [ ] Backup/restore и rollback проверены либо явно неприменимы (например, статика без БД).
- [ ] Есть мониторинг, ответственный и подтверждение владельца на production.

## Если деплой упал

```prompt
Разбери сбой по очищенному от секретов логу: [фрагмент].
Проверь фактическую ошибку, версии runtime, build/start-команды и наличие обязательных
env без раскрытия значений. Исправь минимально, повтори проверки и сообщи результат.
Не меняй платформу, доступы или production-данные без согласования.
```

Не публикуй непроверенный сайт ради срока: зафиксируй блокер и безопасный следующий шаг.
